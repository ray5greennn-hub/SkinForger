# SkinForger 开发历程

2026-09-24 开工，到 2026-11-22 为止。这份文档记的是**每个功能为什么做成这样**，
以及一路上哪些做法被证明是错的。

## 一、目标与边界

做一个**可复用**的 Muse Dash 皮肤 Mod：把单张 PNG 放进皮肤目录就能换皮，不针对任何角色写死。

从头到尾守住的几条边界：

* **没有白名单。** 所有机制对所有角色通用。实机逐一验证过的只有四个角色，
  但代码里没有一处按角色名、部件名或索引特判。
* **只支持 Steam 正版（Windows）。** 和谐版（hexie）资源一律不导出、不读取、不替换、不预览 ——
  连正版骨骼里混着的和谐部件也一样拦掉。
* **Dump 只读游戏原版图集**，从不读 SkinForger 自己合成的图集（否则会把别人的皮肤包导出来）。
* **皮肤包的内容永远不落盘**，只在内存里解码。

## 二、开发原则

这十二条不是一开始定的，是一路踩出来的。每一条背后都有一次事故。

1. **稳定优先，一次只改一个关键点。**
2. **先取证据再修。** 「PNG 被读取了 / 写进图集了」**不等于**「屏幕上用的就是它」。
3. **Preview 正常不代表 Gameplay 正常**，两边分别验证。
4. 改动前备份并记录 SHA256。
5. **不做每帧扫描、每帧重新替换。** 生命周期入口要低频、可预测。
6. 不 patch `SkeletonMecanim.Initialize(bool)`（曾导致栈溢出）。
7. **不在启动期挂全局 Spine Harmony hook**（曾导致崩溃和残留进程）。
8. 不把「读取整张图集 PNG」当作皮肤来源；皮肤来源只认单张 PNG。
9. **不改写角色 Mesh 的 `vertices` / `regionUVs`**（扩框改为渲染时追加几何）。
10. 不使用 `OnPostProcessVertices` 委托（Il2CppInterop 下注册失败）。
11. 结论标注 `[实测]` / `[代码]` / `[推测]`，不把未验证的写成已完成。
12. 皮肤包内容、合成图集永不写盘。

## 三、时间线

### 2026-09 上旬：替换链路成立

* 建立 MelonLoader Mod（验证版本 0.7.4），能进选人、Preview、Gameplay。
* **核心链路定型**：单张 PNG → `Texture2D` → 运行时图集 → `AtlasRegion` → `Attachment`。
  走的是 Spine 资源链，**不是** Sprite —— 这个选择决定了后面所有事。
* 第一个「缓存 key 少了一维」的坑：运行时图集的放置缓存没区分不同 `Texture2D`，
  Preview 算出的扩框位置被 Gameplay 误用，UV 直接越界。key 补上运行时贴图的 InstanceID。
* 扩框判定改用 manifest 记录的**原始**尺寸，当前 PNG 尺寸从解码结果动态读。
* JSON sidecar 定为 v2：`version` / `origin` / `anchorX` / `anchorY` / `rotation`。旧 v1 仍可读。
* 命名为 SkinForger，装在 `Mods\SkinForger\`。
  MelonLoader 只扫描**带 `manifest.json`** 的 Mods 子目录，所以包里必须有一个（内容就是 `{}`）。

### 2026-09 中旬：周边功能

* **自定义加载插画**：钩 `LoadingImg.OnEnable`，从配置列表里随机选图，失败回退原版。
  最终挂到可见父容器上，用 Cover / Aspect Fill（统一缩放、居中裁剪）。
* **帧率上限**：配置文件写 `{"FPSLimit":60}`，0 表示不限制。
  只在初始化和场景初始化时恢复上限，不改 VSync，没有每帧轮询。
* **动画幅度**：JSON 新增 `MovementAmplitude` / `X` / `Y` / `Rotate`，只缩放位移和旋转时间轴的增量。
  坑：Spine 的 `ScaleTimeline` / `ShearTimeline` **继承自** `TranslateTimeline`，
  不先排除就会把缩放也乘上倍率，图片跟着变大。
* **Bad Apple 兼容**：黑白剪影场景里替换过的部件会碎掉 ——
  运行时图集的 UV 被交给了原版小图集去采样。
  解法是等游戏完成最终材质刷新后，一次性把那个场景的材质对齐到 SkinForger 的运行时图集。
  （这条线后面还要反复修五次，见下文。）

### 2026-09 下旬：Dump、缩略图、Preview

* **Dump 的 JSON 成对输出**：Mesh 部件原先只出 PNG 不出 JSON（一个角色 420 张图缺 398 个 sidecar）。
  去掉错误的「只有 RegionAttachment 才写」门槛后，全局 5302/5302 成对。
* **选择界面缩略图**：可 Dump、可替换、可 Reload。
  坑：小精灵的 `order` 从 1 开始，`listIndex` 从 0 开始，混用导致整条链错后一位、角色之间串图。
  统一改用 `listIndex`，并在建立绑定前校验实际图片名。
* **Preview MVP**：独立窗口、角色 / 场景 / 动画选择、播放控制、独立相机和 RenderTexture，
  用克隆的骨架资产，不碰 Gameplay 对象。
  坑：这个游戏的 Spine IL2CPP 包装**不接受**「空资产 + 注入托管数据」这条纯运行时路径，
  必须 `Instantiate` 原资产再让 Spine 自己从 JSON 解析。
* **Dump 的性能与生命周期**：同一图集只读回一次；manifest 最后统一写；临时对象立即销毁。
  Dump 之后的刷新改为「只刷索引」—— 此前 Dump 完贴图会整个消失，
  因为那次刷新把正在使用的运行时图集销毁了。

### 2026-09 底 ~ 2026-10 初：两次事故

* **程序集自引用**：一个候选 DLL 因为方法复制产生了自引用，MelonLoader 直接拒绝加载。
  规则：安装候选前必须检查无自引用。
* **全局 Spine hook 事故**：一个诊断组件在启动期挂全局 Harmony hook，
  反复触发 `0xC00000FD` 原生栈溢出；崩溃快照还锁住 DLL，留下无窗口的残留进程。
  该组件永久停用，诊断改为**零 Harmony** 的被动只读。
* **进程会话清理**：用一份会话账本记录每次启动，下次启动时只清理
  「已请求退出、身份完全匹配、没有可见窗口」的那**一个**旧进程。
  不按进程名批量结束，崩溃快照不在处理范围内。身份闸门有九项，全部满足才动手。

### 2026-10 上旬：贴图读取问题收尾

* **旋转存放的矩形泛化**：支持 0 / 90 / 180 / 270°（静态验证 1058 个资源 0 误差）。
* `RegionAttachment` 的私有 Region 丢了 rotation 信息，导致部件错乱 —— 保留原 `degrees` / `rotate`。
* **多边形打包矩形互相覆盖**：Spine 的多边形打包**允许**不同部件的外接矩形相交，
  而完整画布替换会向整个矩形写像素，后写的覆盖先写的。
  解法：所有 Mesh 替换统一申请独立、不重叠的新矩形。
* **PMA 往返**：游戏图集是预乘 Alpha，Dump 直接存 PNG、导入时又预乘一次 → 半透明边缘发暗。
  导出时先反预乘（`a=0` 时 RGB 清零）。
* **Dump 极慢**：每写一个文件都完整保存一次约 2.2 MiB 的备份状态，约 300 次共 125 秒 ——
  改为整个会话结束时保存一次。
* **横向细条纹**：运行时贴图被设成 Point 过滤，原版是 Linear。改成 Bilinear 后消失。
* 界面首次打开卡约 50 ms，是 Unity IMGUI 首次初始化的成本。
  试过预热，**只是把卡顿挪到了游戏帧**，放弃。

### 2026-10 中旬：Preview 契约与一次重要回退

* **Preview 碎片化的根因**：Preview 克隆到的 Region / UV 已经是运行时图集的坐标，
  但绑定的仍是游戏原始贴图 —— 「新 UV + 原贴图」。
  解法：从游戏原 `.atlas` 恢复 Preview 私有的原始坐标契约。
* **一次失败的扩大化**：把 81 个部件统一改成私有整图 + `0..1` UV，结果严重碎片化加白毛边。
  原因是最终渲染器只有一个 material，部件的数据阶段和渲染器的最终阶段不属于同一套绑定。
  **回退**，并把 Preview 冻结为一个已验证的状态。
* **当时的扩框架构结论**：「读取贴图」和「扩展几何」必须分开 ——
  只改 Region / UV 不会让 Mesh 变大。这条结论正确，但它导出的那套做法（改写 Mesh）后来被推翻。

### 2026-10 下旬：性能与拓扑安全

* **冷构建提速**：先只读 PNG 头拿尺寸，一次性把图集扩到最终大小，最后统一上传 GPU。
  原先逐张扩容、逐张 Apply，73 张图要约 19 秒。
* **Preview 首开 3.7 秒**：Preview 没能复用 Gameplay 已建好的图集，又从头建了一张。
  改用同一套 key 生成规则，并预检复用的是同一个实例。
* **调和映射（后来被取代）**：加权 Mesh 的内部顶点改为连续调和映射，
  提交前检查三角形是否翻转或退化。碎片化消失了，**但动画拉扯还在** ——
  这是「改写 Mesh」这条路的最后一次尝试。
* 图集热复用：同一骨架跳过重复构建；缓存上限随实测调整（96 → 112 → 256 MiB）。
* **「某个角色没替换」的虚假警报**：原因是没在界面里选 Root（选择值为 -1），
  不是算法失败。此后「没反应」先查选择状态。

### 2026-11 中旬：扩框突破

**这是整个项目的技术核心。**

此前 Main 会改写所有角色 Mesh 的 `vertices` / `regionUVs` ——
扩框看得见了，但原生变形被破坏（锯齿、拉扯、碎块）。

新方案：**Attachment 一个字节都不改。** 每帧在 Spine 算完骨骼变形**之后**，
在临时网格缓冲里做两件事：

1. 把 UV 映射到扩展 PNG 中原图所在的矩形；
2. 追加一圈补充三角形，盖住扩出来的那部分画布。

逐步验证过去：单个部件 → 非对称留白 → 所有 Mesh 部件 → 结算界面与 Preview。
期间还解决了两个边界：

* **结算界面是 UI Spine**（`SkeletonGraphic`），不走 `SkeletonRenderer.LateUpdate`，
  要单独一条发现路径；
* **结算动画带 Spine 裁剪**，走 `AddSubmesh` 而不是 `BuildMeshWithArrays`，
  所以新增「裁剪帧模式」：不预留空间，在本帧缓冲里按原样 UV 定位目标再追加。

完整原理见 `docs/expansion/扩框机制说明.txt`。

### 2026-11 中旬：工程化

* **二十来个独立 melon 合并成一个 `SkinForger.Core.dll`**（4 个看门狗文件合并成一个 exe）。
  验证方式：先确认每个模块的源码与部署版 IL 完全一致，合并后再做 IL 比对，方法逐条不变。
* **看门狗 2.0**：
  * 只清理**游戏自己的**进程（游戏目录内的程序，以及游戏的 WerFault）——
    旧版曾把挂在游戏下的输入法当成残留误杀；
  * 「文件已释放」改为**可写**检查（旧版用只读方式打开，被占用时也会报已释放）；
  * 识别崩溃类型、崩溃后等待 Windows 错误报告、用 Restart Manager 查出占用者；
  * 文件实在释放不了时（零线程快照），把旧文件改名再复制新文件，部署照样完成。
* **只支持 Steam 正版**：和谐资源在读取、Dump、缩略图、预览各个入口全部拦掉。
  发现：正版骨骼里本来就混着和谐部件，有的小精灵还有一整张和谐图集；
  有些和谐专用部件**名字里甚至不带 hexie**，只能靠「只在和谐皮肤里出现」来识别。
  坑：拦掉部件之后，Preview 预先清点「应该有几张图」时仍然算上了它们，
  两边数字对不上（57 对 55），Preview 就静默回退到旧路径 —— 拦截必须在清点之前完成。

### 2026-11 中旬：皮肤包 `.sfskin`

**为什么做**：合成图集本来就只在内存里，唯一的移植入口是磁盘上的裸 PNG 文件夹 ——
复制文件夹再打包进别的平台就能直接移植。
对策是「**用裸文件创作，用包分发**」。

* **目录分工**：`SkinCreator\` 是创作区（Dump 输出、改图、设置都在这里），
  `Skins\` 是玩家放 `.sfskin` 的地方，`ExportSkin\` 是导出位置。
* **格式**：文件头（标识 + 版本）+ AES-256-CBC 加密的 ZIP + 末尾 SHA-256 校验。
  普通解压工具打不开，改一个字节就因校验失败而拒绝读取。
  **局限写在源码注释里**：密钥种子是源码里的常量，这是「标准工具打不开的容器」，
  不是密码学意义上的保密。真正保护皮肤作者的是导出时记录的 Sharing 选择和项目条款。
* **只在内存里加载**：启动、点 Reload、运行中目录变化时，把每个包解码到内存，
  挂载成虚拟目录。Main 和 Preview 读文件的地方（共 42 处）全部经过一层虚拟文件垫片 ——
  路径在包里就从内存返回，其他路径照常读盘。
  坑：虚拟目录名必须用固定的安全名字，因为 Main 会拒绝路径里含 `atlas`、`cache`、`backup` 字样的资源。
* **只打包改过的图**：包里只有 manifest、创作者改过的图和这些图的锚点 JSON。
  没改的部件不进包，玩家那边自动显示自己游戏里的原版。
  一个角色的包从约 2 MB 降到 8 KB，而且**包里只有创作者自己的作品**，不再转发游戏原版美术。
* **怎么算「改过」**（后来扩充到五条）：有备份历史 / 内容和记录的哈希不同 /
  尺寸和原图不同 / JSON 的缩放、幅度、偏移、旋转被改过 / **整张擦成全透明**也算
  （作者要的就是「不显示」，旧规则会把它判成没改过，于是包里缺图、游戏原版的头发盖在新画的头上）。
* **Dump 隔离**：选中皮肤包时 Dump，导出的图全是碎片 ——
  Dump 按原版图集的坐标切图，而画面上用的是合成图集。这同时是一条泄露途径。
  解法：Dump 开始前把相关角色临时切回 Original 并恢复原版图集，结束后还原，失败也一定还原；
  再加一道硬保险，Dump 期间查询这些角色的皮肤路径一律返回空。

### 2026-11 中旬：皮肤库

给「只想用皮肤、不画皮肤」的玩家用。界面只用玩家熟悉的词。

* 放进 `Skins\` 的包自动出现，一张卡片一个皮肤，一个开关开关它。
* **加载顺序**：`SkinCreator`（自己正在做的）> 已开启的皮肤（后开启的在上）> 游戏原版。
* **按图片叠加，不是整个角色替换**：上层皮肤只替换它自己有的那些图，其余仍来自下层。
* 图片按**部件身份**（图集 + 区域 + 部件名）对应，**不按文件名** ——
  因为两次 Dump 之间，同名部件谁被加后缀 `_2` 可能正好相反。
* **冲突提示**：开启一个皮肤时，如果它改的角色已经有别的皮肤也改了，先逐个角色列出冲突，
  让玩家决定。不禁止同时开启 —— 混用本来就是这个功能的意义。
* 一条反直觉的规则：**Root 只有玩家点了 Root 才生效**。
  实现上每个角色有两个隐藏变体（「只有皮肤」和「皮肤 + 我的作品」），
  关掉皮肤后分别回落到原版或 Root。后来简化为「点 Root 就完全只显示创作者文件夹」。

### 2026-11 下旬：文字与字体

* 只替换角色名 / 服装名 / 皮肤名 / 描述 / 卡片 / 技能 / CV / 各类对话 / 节日台词 /
  加载提示，**不导出游戏全部文本**。文件按语言分目录。
* **替换原理**：游戏读文本有两条路 —— 缓存的 JSON 表和解析好的对象表，两条都改。
  一开始还加了「只在游戏原文就是你记录的那句时才替换」的匹配闸门，
  后来**取掉了**：一条改过的提示因为对不上就无声无息地不生效，
  「一条没人看得见的规则不是保险，是陷阱」。改成「改过就写」，对不上时在日志里说一句。
* 同时把那份用于区分「改过 / 没改」的原文记账**移出作者要编辑的文件**，
  存到隐藏的基线文件里 —— 作者看到的文件里只有要改的那一行。
* **加载提示找不到**：游戏在 SF 启动**之前**就读完了它，钩子装上时已经错过。
  改为直接从游戏的配置对象里取出各语言的提示表。
* **字体替换走了五轮**：
  1. 先 `new Font()` 再从文件加载 —— `new Font()` 已经建了一个空字体，文件没进去；
  2. 换个顺序 —— 两种方式都得到空字体。结论（实测）：**这个 Unity 版本不能直接从字体文件加载字体**；
  3. 改用 Windows 已安装的字体 —— 英文系统字体成功，中文字体因为没装而提示；
  4. 装了还是不行 —— 字体查看器的「安装」只装给当前账户，Unity 看不到；
     **必须「为所有用户安装」**。界面改成明确提示 + 「显示字体文件」按钮；
  5. TextMeshPro 仍然不换 —— 它读字形时调的那个接口对「已安装字体」没有字体数据，
     改为直接从字体文件读字形（2048 多图集，放得下中文）。
* **换字体引出的三个排版问题**：
  * 居中的单行文字换宽字体后向两边溢出 → 按宽度比例缩小字号，切回时恢复。
    一开始只处理「溢出方式 = Overflow」的，漏掉了**框宽为 0** 的那种（框宽 0 时实际不换行）。
  * 技能描述不换字体 → 游戏会在面板显示时**重新设置**字体，
    所以必须钩住 font 的 setter，而不是只在出现时换一次。
  * 角色名被切掉下半截 → 走了六版才找对：那行字的父级就是游戏自带的**名字遮罩**，
    而前几轮诊断的是另一棵树上的同名标签（「同名不同物」）。
    最终解法是 uGUI 自带的开关 `maskable = false`：整行完整画出，**布局一个像素都不动**。
    并且做成内置规矩 —— 所有角色 / 小精灵名字一律无视名字遮罩，与换不换字体无关。
* **一个连带事故**：改了小精灵的**英文名**之后，她的皮肤失效了 ——
  Main 正是用英文名去找皮肤文件夹的，而文字替换改的就是那张表。
  教训：做文字替换前没检查名字字段是否同时被当作标识使用。

### 2026-11 下旬：打字不能影响游戏

在 SF 的输入框里打字，Enter 和空格会触发游戏操作。这个问题走了五层才解决：

1. 关 Rewired 键盘控制器 → 无效；
2. 暂停 Rewired 玩家 + 拦截 `UnityEngine.Input` 托管包装 → 日志显示拦截开启，仍无效；
3. 拦截 Unity 读键盘的底层函数 + 全部 Rewired 按键查询 → 每次打字拦下十几万次，**仍无效**；
4. 查代码才发现：游戏**还用了 Unity 新输入系统**，前三层全都不在这条路上；
5. 打字时直接 `DisableDevice(Keyboard.current)`，结束时恢复。前几层保留。

**教训**：前两版没先查清游戏到底用哪几种输入方式就开始一层层加拦截，白费两轮。

顺带还有一个滚轮穿透：在 SF 窗口上滚滚轮，游戏的选歌列表也跟着换 ——
窗口屏蔽只挡了 uGUI 的事件系统，而游戏的滚轮读的是 `Input`。
解法是鼠标在 SF 窗口上时，让滚轮相关的查询对游戏返回 0。

### 2026-11 下旬：声音

* 名字来源：游戏资源清单里的音频条目，按配置对到角色（排除和谐）。
* **拦错了管理器**：游戏里有两个 `AudioManager`，第一轮拦的那个不负责播语音。
  真正播语音 / BGM / 战斗音效的是另一个，而战斗音效还会**先预加载进缓存再直接播** ——
  所以缓存里的也要换掉（并记下原版，取消替换时还回去）。
* **打歌中的语音**（受伤、空挥等）从游戏的语音设置表里补进列表。
* **武器 / 打击音效**不属于任何角色、名字事先不知道 ——
  新增「最近播放」列表：启动后播过的声音都列出来，打一首歌就能看到名字。
* 可以直接**静音**（写一个名单文件，可手改），播放时换成一段 0.05 秒的静音，回调照常执行。
* **语音和台词挂钩**：台词气泡在语音播完才消失，所以替换语音后气泡跟着新语音长度；
  静音时按文字长短给几秒。对应关系是游戏自己的「台词组 + 序号」。

### 2026-11 下旬：第二套皮肤、切换图标、逐帧皮肤

* **第二套皮肤**：有些角色有两三套皮肤，第二套的立绘和动画原先既不导出也不替换 ——
  Main 靠「物体名包含角色英文名」认角色，而第二套的名字里没有。
  解法：读角色配置里的皮肤列表，把其他皮肤的各个 show 也交给 Dump；
  认角色时改为「物体名包含某个皮肤资源名就归到那个角色」（取最长匹配）。
* **一次卡死**：选第二套进游戏打歌卡死 50 秒，图集被扩到 2048x16070 ——
  Main 会把文件夹里**每一张** PNG 重新放进图集，刚 Dump 的原图也不例外。
  解法：其他皮肤的图集只使用「改过的」图，没改的原图当作不存在，游戏原图保留。
  没有一张改过的图时，直接把这个物体交还给游戏，SF 完全不处理（开销约等于零）。
* **切换立绘的图标**：第一版找错了字段（把头像当成了切换按钮的图）。
  改为从角色页本身学：界面刷新后读每个按钮实际显示的图。
  导出时不能按 sprite 的矩形裁（紧密打包的 sprite 会被截掉），
  改为按 sprite 自己的网格三角形逐像素复制。
  图标也支持扩框：PNG 比原图大就按比例放大图标的框（以中心为准）。
* **逐帧皮肤**（俗称猫皮肤）：它其实**也是 Spine**，不是图片序列 ——
  「逐帧」是 Spine 动画里每一帧换一张图，所以部件特别多（一套上百张）。
  配置里并没有标记它的字段，只能靠资源名识别。
  它预览不出来的原因很意外：Preview 选主体时给名字含 `cat` 的渲染器扣了 10 万分
  （原意是排除小猫影子之类的附属物体），而逐帧皮肤的主体名字本身就带 `cat`，
  于是一个都选不上，**静默跳过**。
* **逐帧查看**：动画行下面加一行 `Frame < ▶/|| >`，
  点击即暂停并跳到上一个 / 下一个「换图」的时刻（当前动画所有附件时间轴的关键帧），
  没有换图关键帧时按 1/30 秒一步。
* **一个文件夹一个锚点文件**：逐帧皮肤有上百张图，不需要每张一个 JSON。
  改为一个图集文件夹一份 `anchors.json`，逐图 JSON 优先。

### 2026-11 下旬：锚点规则定稿

这条线改了七八轮，因为它要回答一个很难的问题：
**画师把画布扩大之后，原来那张画应该钉在哪里？**

* 需求很明确：「无论怎样扩大画布，初始焦点都不会改变，除非用 JSON 改了它」。
* 第一版思路是**在大画布里自动找原画的位置**（而不是假设居中）。
  为此写了一个纯 .NET 的匹配器：粗搜 + 细搜，评分 = 透明度差 + 颜色差。
* 然后是一连串「原图从哪来」的问题：
  * 用备份副本当原图 → 错，那是**改过的**版本（Dump 写文件时没登记到备份系统）；
  * 从 manifest 重建 → 旋转存放的部件裁切和实际原图对不上；
  * 最后改为**直接调用 Dump 自己的裁切代码**，拿到和导出时一模一样的原图。
* 评分也改了三轮：
  * 画师把扩出来的画布整片填了底色 → 旧评分连「原图透明的地方」也比，到处都一样差 →
    改为**只比较原图有画的地方**；
  * 画师把部件**整体重新上色** → 颜色比对失效 → 加一条**只比透明度的轮廓比对**，两者取更有说服力的；
  * 候选原图是从图集空白处读出来的**整张全透明** → 它和画布上的空白「完全一样」，
    于是得到假的满分，把锚点钉在一块空地上 → 画了东西的像素少于 2% 直接作废。
* **最重要的一条规则是最后才想明白的**：
  自动匹配每次 Reload 都重算，于是画师在上方加空间、焦点跟着往上跑，**抵消了他的操作**。
  正确的模型是：**焦点是一颗钉子**，在上方加空间就该把画往下推。
  所以改成**只算一次** —— 刚 Dump 的部件第一次被扩大画布时算一次，写进 JSON 后永久固定。
* **最终优先级**：玩家手改的 `anchorX/Y` > JSON 的 `canvasAnchor`（九宫格，对应画图软件的「画布大小」对话框）
  > 自动找原画 > 居中。
* 结论：**大改过或重画过的部件，自动比对本身不可靠**，用 `canvasAnchor` 指定最准。
  这不是失败，是把能自动的自动掉、把不能自动的交回给作者。

### 2026-11 下旬：offset / rotation 做成刚性变换

* 规则：扩大画布导致动作不同可以理解；但**单纯移动或旋转时，网格变形必须和原版一模一样**。
* 旧做法的问题：offset 让画在网格里滑出去，滑出去的部分由补充几何的外圈带着动，摆动方式就变了。
* 新做法：offset **不再参与画布计算**。每帧在 Spine 算完变形之后、写进网格之前，
  把该部件的全部顶点（含外圈）做一次**刚性变换** ——
  先拟合出这一帧「图片像素 → 变形后顶点」的映射，再按它平移、绕锚点整块旋转。
  变形后的形状完全保留，只是整体挪 / 转，跟着部件这一帧的朝向走。
  离线验证：平移在所有顶点上一致（误差 1e-7），旋转保距。
* 边界：只对网格部件、只在 SkinForger 自己的图集上；
  普通四边形部件的 offset 仍由 Main 处理（见 `docs/为什么重写了Main.md`）。

### 2026-11 下旬：性能三轮

每一轮都是「先量，再改」。

1. **第一轮**：发现 Main 出厂时开着调试开关 ——
   每次加载打印几百行诊断，而且每写入一张图就对整张图集（最大 512x7711）重算一次校验和。
   **插值字符串在调用前就求值了**，所以即使不输出也照样算。关掉开关，顺带：
   把每 3 秒扫描全部约 3000 个文字组件改成事件驱动 + 20 秒兜底；
   文本目录改用文件监视器而不是每 2 秒递归扫描。
2. **第二轮**：开着 Preview 时 Reload 要 3.2 秒。拆开看：
   Preview 自己的骨骼约 1 秒是**完全白做**的（Reload 前已销毁、Reload 后会重建）；
   不在场景里的 prefab 资源也被重新套皮（没人显示它们）。
   Reload 期间跳过这两类，并缓存按名字认角色的结果。
3. **第三轮**：仍有 0.6~0.7 秒。继续量：
   Main 对每个扩大过的部件都会再裁一次原图并逐像素扫一遍，而那些值**只被调试日志用到** → 跳过；
   热复用因为「材质还没建好」判不出透明方式而整张重建 → 改用骨骼数据里图集的主材质来判断；
   已解码的图片在 Reload 时被整批清空 → 文件大小和修改时间都没变的放回去，只重新解码改过的
   （一次 Reload 的解码次数从 76 降到 1）。

最终：只改 PNG 的增量 Reload 约 5 ms；完整重载约 0.7~0.8 秒。

### 2026-11-17 ~ 19：把 Main 整个重写

起点是一个早就记下的已知限制：**Main 没有可编译的源码** ——
它是一条 Cecil 二进制补丁链的产物。这既不满足 GPL 的「对应源码」义务，也没法长期维护。

为什么做、怎么做、怎么核验「真的不含上游代码」，以及
**那三类「在源码里看不见的契约」**（方法名、参数名、字段名）——
写在 `docs/为什么重写了Main.md`。那是这个项目最值得别人读的一篇。

### 2026-11 下旬：收尾的几件小事

* **皮肤包自带作者说明**：作者放一个 `readme.txt`，打包时可勾选；
  别人第一次启用这个皮肤时在屏幕中央弹出一次，之后靠卡片上的按钮随时再看。
  坑：中文记事本的「ANSI」是代码页 936，不认就是满屏乱码 ——
  解码顺序是严格 UTF-8 → 936 → 宽松 UTF-8，而且 936 的 provider 用反射注册，
  这样格式代码仍然是「纯 .NET、无额外依赖」。
  另一个坑：自动弹窗的判定只能在 Layout 事件做 ——
  在 Layout 和 Repaint 之间冒出来的窗口会让 IMGUI 整帧抛异常。
* **首次安装只生成最少的东西**：启动后只出现 `SkinForger\Skins`，
  `SkinCreator` 只在玩家开始做皮肤时才生成。
  做这个时发现一个**会丢玩家数据的隐患**：有一条旧版迁移逻辑，
  在「创作目录不存在而 `Skins` 存在」时会把整个 `Skins` 搬走 ——
  而 `Skins` 现在正是玩家放皮肤包的地方。已封死。
* **没有 DLC 的正版玩家能不能用**：能。
  关键证据是安装清单里**只有一个 depot** —— 那个 DLC 不往硬盘上放任何文件，
  它只是解锁游戏里本来就在的内容。所以有没有 DLC，SF 看到的文件、配置表、角色索引完全一样。
  顺带补了一条「这个皮肤包不属于你这版游戏」的提示 ——
  否则匹配不到任何东西时它**一个字都不说**，正是最难回答的那种反馈（「我装了，没反应」）。

## 四、已否决的做法（不要重新尝试）

每一条都试过，每一条都有具体的失败证据。

**替换链路**
* 把「读取整张图集 PNG」当作皮肤来源。
* patch `SkeletonMecanim.Initialize(bool)`，或任何每帧重新应用替换。

**Hook 策略**
* 启动期挂全局 Spine Harmony hook。
* 全局 patch `Renderer.set_material` / `set_sharedMaterial`（setter 重入链 → 栈溢出）。
* 单独做一个诊断 Mod 走调查路线（改为在主程序里做受控 tracing）。
* 按哈希白名单绑定旧版 DLL —— 对不上就**静默禁用**，功能在却没人启动它。

**Preview**
* 统一 `0..1` UV 的全量私有替换。
* 克隆 prefab 或挪动场景里的实例。
* 重定向游戏相机。
* 往空的骨架资产里注入托管数据。

**扩框**
* 改写角色 Mesh 的 `vertices` / `regionUVs`（包括后来那套调和映射）。
* 把 Mesh 换成普通四边形部件。
* 私有 Mesh 绑定。
* 重建整张图集。
* `OnPostProcessVertices` 委托（Il2CppInterop 下注册失败）。

**其他**
* IMGUI 预热（只会把卡顿挪到别处）。

## 五、反复出现的几个教训

写在最后，因为它们是从十几次独立的事故里收敛出来的，不属于任何单个功能。

1. **「读到了」不等于「用上了」。**
   PNG 被读取、写进图集、UV 被更新 —— 这些都不证明屏幕上显示的是它。
   最终绑定在哪一层，必须单独取证。

2. **静默失效比崩溃危险得多。**
   哈希白名单对不上、反射取字段返回 null、名字匹配失败、数字对不上就回退旧路径 ——
   这些都**不报错**，功能就是没有了。所以后来每个模块都要自报状态。

3. **同名不同物，同名不同义。**
   UI 组件名会出现在多棵树上（诊断了三轮才发现在看另一个同名标签）；
   方法名和签名都一样、含义却被改了（`GetCount` 从「表有几行」变成「这个角色有几套皮肤」，
   Preview 直接空白，所有按名字比对的工具都查不出来）。

4. **缓存 key 少一维，表现出来是画面错乱。**
   少了运行时贴图的 InstanceID、少了内容指纹、页尺寸是共用对象却按部件逐个记 ——
   症状都是 UV 越界或读到别处。

5. **工具会假绿，也会假红。**
   按名字在整个程序集里搜「有没有被调用」，会把撞名的判成已调用（假绿，盖住了一个真 bug）；
   不懂「一个文件夹一份锚点文件」的检查会报假 FAIL。
   所以判定标准是「**0 未解释**」，不是「0 FAIL」—— 每一条异常都得有一句解释。

6. **先查清机制，再动手拦。**
   输入拦截那五层、Bad Apple 那五版，都是因为没先搞清楚「游戏到底走哪条路」就开始加补丁。

7. **自动化要在不可靠的地方交回控制权。**
   锚点自动匹配对重画过的部件不可靠 —— 正确的做法不是把它调得更聪明，
   而是给作者一个明确的手动选项（九宫格），并且**只算一次**，不要跟玩家的操作打架。
